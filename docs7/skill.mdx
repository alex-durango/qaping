Two jobs, one file. SETUP authors `QA-PLAN.md` — the committed list of checks
this game must pass. RUN executes it per patch: pick the affected checks,
build, ship the build to real human playtesters, and report ONE typed outcome
per check — never a vibe. The check is the unit of value: its id rides from
the plan onto the wire, into the report, and into the server history. Over
patches, checks migrate from human rounds to repo code tests, so QA gets
cheaper. Checks are what the game must always do; BUGS are what it does wrong
right now, and they live on the game's issue board, where a fix you claim
turns verified only when a playtester says it is gone. The four MCP tools run the
loop — `qaping_playtest`, `qaping_results`, `qaping_wait`, `qaping_issues`.
The CLI hosts builds and manages server workflow with `qaping rounds`.

## Ground rules (read before filing anything)

- **Playtesters are real people, and a round outlives a quick turn.
  Decide at filing time: wait, or park.** A session takes real minutes, often
  hours, to be claimed and played. Which of the two endings this round gets is
  chosen BEFORE you file, not discovered when pending surprises you.
  - **WAIT — short rounds you can sit through.** Each `qaping_wait` renews the
    lease that keeps the round visible to new claimants. The moment a filing
    returns pending, SPAWN A BACKGROUND TASK that loops `qaping_wait` with the
    ping_id until results arrive, and keep working on other things — that is
    the intended shape for a short playtest round. Only if your harness
    has no background tasks: keep polling in the foreground. A one-shot print
    mode where neither is possible is not a WAIT round at all — it is a PARK
    (below): file with an explicit `deadline_seconds` and `qa_context`, say what is pending, and ask to be re-invoked to
    collect it — never promise polling you cannot do (an ended session cannot
    poll). A round already filed on the default lease is saved on the server anyway;
    flag it as likely to expire unclaimed.
  - **PARK — long or overnight rounds.** For a session nobody will sit
    through — an overnight run, `n_target > 1` on a small pool, a native round
    whose claim is slow, an explicit "check tomorrow", or a one-shot mode —
    file with an explicit `deadline_seconds` sized to the span you are willing
    to wait (the tool schema states the ceiling) plus an `idempotency_key`,
    and `qa_context: {checks: [...], note: "<patch>", commit: "<sha>",
    pr_url: "<PR URL>"}` (omit unknown optional fields). The round and this
    private context are saved in ONE transaction. No separate add or local
    write is needed. Tell the user what is pending and what will collect it,
    and end the turn cleanly.
  - **A recorded parked round is an honest pending end; an unrecorded "I'll
    check later" never is.** Never park on the default lease: with no explicit
    `deadline_seconds` an unwaited round leaves the feed within minutes and
    expires unclaimed (a round died exactly that way, live). On resume,
    collect the recorded round — never file a duplicate.
- **Costs are duration-billed**: 2 credits per minute of play, per playtester
  (`est_minutes × 2 × players`). State the estimate to the user BEFORE filing,
  and set the wait expectation honestly in the same message: claim time is
  unbounded on a small pool — "push now or wait for QA" is their call, made
  informed.
- **Evidence varies by platform — never promise what a platform does not
  ship.** macOS and iOS rounds return a screen+voice recording plus an inline
  [mm:ss] think-aloud transcript. Windows rounds return a recording, and a
  transcript only when the tester recorded with our recorder app — read
  `transcript_status` on each result: `'ok'` means an inline transcript,
  `'unavailable'` means a Game Bar session with NO transcript. It is a
  per-session fact, never promise one for a Windows round; plan to watch an
  `'unavailable'` recording for timestamps. WEB rounds return answers only — no
  recording, no transcript: the tester's option picks and free text are the
  entire deliverable, which is why every check rides an option step.
- **Pay is flat per session, never per bug.** Never offer or imply a bounty.
  Never steer a tester's OS-security decision (stopping at a warning is their
  penalty-free call); steering their PLAY — steps, links, forced states — is
  the job.
- **Machine replay is not self-serve yet.** Never claim an automated replay
  ran. The only automated rung you can run today is a `rung: code` test in
  the dev's own repo/CI.
- **QA-PLAN.md is the dev's file.** Commit it only with their approval; never
  delete or demote a human check without them agreeing.

## Open rounds — collect FIRST

Before ANY qaping work in a repo — a new run, plan edit, or "did it come
back yet?" — run `qaping rounds --game <game_slug> --json`. This lists
unprocessed work on the server. Follow `next_cursor` until the queue is
covered. `--all` includes processed history; `--processed` reads history only.
Omit `--game` to discover older rounds without a slug. Identify those by their
real build and saved context; never invent missing notes or adopt another game's work.

- **Still pending:** leave it on the server, say what is waiting, and never
  file another round for the same checks/build. A read never renews its lease.
- **READY or expired:** claim it with `qaping rounds claim <ping_id>` before
  collecting. The JSON returns a collector `token`, `workflow.revision` and
  `response_ids`. Another agent cannot collect while that claim is live.
  Keep those values for completion; renew at least every 20 minutes by repeating
  `claim` with `--token <token>` (the claim lasts 30 minutes). A lost response
  is retried with the SAME token; the CLI's error prints the token to reuse.
- Fetch `qaping results <ping_id>` / `qaping_results` and perform the full RUN
  report ritual. `qaping rounds show <ping_id>` reads private context and any
  earlier report. Save the final agent report with `qaping rounds complete`
  as described below; reading results alone NEVER marks work processed.
- **Expired:** report the actual results, including partial results if any.
  Mark unanswered selected checks NOT-ASKED. Complete the report, then offer a
  refile with an appropriate deadline. Expiry does not erase evidence.
- **Another collector holds the round:** leave it to that collector. If a
  session dies its claim expires; a later session can recover the work.
  Release deliberately with `qaping rounds release <id> --token <token>`.

A failed login, missing round or network error is NOT an empty queue. Check
`qaping whoami` and resolve the error before filing a replacement. A processing
conflict means something changed: read the workflow and results again. A late
response or changed transcript reopens a processed round while preserving the
previous report. Collect the new evidence and update the existing PR comment.
Before posting comments or filing external issues, search for the round id and
existing board external_refs. Use a stable `qaping-round:<ping_id>` marker in PR
comments and update a matching comment on retry. A server claim cannot make an
external GitHub write atomic with report completion.

**Upgrade once:** if this repo has `qa-open-rounds.json` or `qa-rounds.jsonl`,
run `qaping rounds import --dry-run`, then `qaping rounds import`. It validates
both files before any request, imports owned rounds once, and preserves the
original files byte-for-byte. Unknown or wrong-account IDs fail loudly; fix
the login and retry. The server retains old records under `workflow.legacy`,
including historical verdicts and follow_ups. Import never overwrites a live
build, status, report or newer patch context. It does not invent a game for
old rounds without one. After import, STOP reading or writing those files.
They are archival backups only. Never delete them automatically.

The server is the machine truth for execution history. `QA-PLAN.md` remains
the dev-readable contract defining the checks; its old `state` and
`last_verified` fields are historical annotations, never inputs to run selection.

## The issue board — bugs live here

Checks are the standing contract; bugs are what is wrong today, and they live
on the game's issue board — one board per `game_slug`, numbered `#1, #2, …`
for the life of the game, read and moved with `qaping_issues`. The board is
what carries a bug across rounds: the checklist a round hands the playtester
is built from it, and it is the only place a fix can ever be confirmed.

| status | who moves it there | how |
|---|---|---|
| `open` | you (`action:'create'`), or a playtester filing a bug from inside a round | the live state, and where a regression lands |
| `fixed` | YOU only (`action:'fixed'`, `build` REQUIRED) | a CLAIM, not a verification |
| `verified` | a PLAYTESTER only — enough "Gone" answers on a round filed AFTER your claim, against the build that claim named | there is no verify action and there never will be |
| `closed` | you only (`action:'close'` + reason wontfix / invalid / duplicate / cannot_reproduce) | leaves the checklist; never turns green |

Every attached issue gets ONE of four answers: **Still here**, **Gone**,
**Couldn't test** (they reached it and still could not tell), **Didn't reach**
(they never got to that part of the game). Only the first two say anything
about the bug at all.

A "Still here" on a `fixed` or `verified` issue REGRESSES it back to `open`
and counts the regression. A "Gone" on an issue nobody claimed fixed changes
nothing — it may simply not have reproduced this session, and the board
records that as a not-seen streak for you to act on (close it
`cannot_reproduce` once you believe it).

- **Green costs more than one player on anything serious.** A "Gone" on a
  claimed fix banks ONE confirmation per distinct playtester: a `blocker` or a
  `major` needs TWO before it turns `verified`, a `minor` or `cosmetic` needs
  one. Under the bar the results say `1 of 2 confirmations` and the issue stays
  amber — that is a fix HOLDING, not a fix that failed. Buy the second
  confirmation with the next round; never re-claim to hurry it, because a fresh
  claim resets the count to zero.
- **A freshly verified issue rides one more round.** It comes back on the next
  checklist labelled "verified last round — still gone?", then drops off for
  good. A "Gone" there reconfirms and moves nothing; a "Still here" is a
  regression, which is the only reason the lap exists.
- **The checklist is sized to the session, and it rotates.** A round carries
  `6 + 2 per five minutes` issues up to a ceiling of 20 — 8 on a 5-minute
  round, 18 on a 30-minute one — in this order: pinned, then claimed-fixed,
  then the confirmation lap, then open ones by severity and
  least-recently-attached. That last key is the rotation: a minor filed weeks
  ago comes back round instead of starving behind the blockers. The filing
  result names exactly what it attached and what it left off — read it rather
  than assuming the whole board rode.
- **Pin the issues a round exists to answer (`issues` on the filing).** The
  seqs you just claimed fixed, and anything the board reports as never
  answered, go in the filing's `issues` array; they are placed ahead of even a
  blocker. Never pin more than the round's own cap — an over-long pin list is
  REFUSED, not trimmed, because the overflow would silently never be asked —
  and never pin a seq that is closed or not on this board, which refuses the
  filing too.
- **Give every issue an `area` (MUST).** Set it on `create` (or repair it with
  `edit`): one or two words a player recognises — "camp screen", "first
  battle", "settings" — never a file, a class, or a system name. The checklist
  GROUPS by area, so a player facing eighteen rows reads a route through the
  game instead of a list, and a board of thirty bugs reads back to you as a map
  of where this game breaks.
- **Act on every "never answered" issue (MUST).** An issue attached to three or
  more rounds that nobody has answered either way is not bad luck: players are
  not reaching it, or cannot tell what it is asking. The results block and the
  board both name them. Do exactly one of three things in the turn you read it
  — pin it on the next filing, give that round a `setup` link and a step that
  walks a player to it, or close it — and say in the report which you chose.
  Letting it ride another checklist unread is the one option that is not open.
- **The board is the source of truth for bugs; the dev's GitHub issues are
  the mirror (MUST).** File it on the board first, then `gh issue create` for
  the dev's own triage, then put that URL back on the board with
  `action:'edit'` + `external_ref`. A bug that lives only in GitHub is never
  re-checked by anyone, because only the board rides a round.
- **Issue titles and bodies speak player language (MUST)** — the same rule
  the steps live under, for the same reason: a stranger reads them
  mid-session on their own machine. "The shop closes when you press B twice",
  never "NRE in ShopController.OnClose". No file paths, no stack traces, no
  ticket ids. Title ≤120 chars, body ≤1000, `area` ≤40.
- **No build, no claim (MUST) — and it has to be THE build.** `action:'fixed'`
  takes the exact build URL the NEXT round will play, and the claim happens
  BEFORE that round is filed. A fix claimed after the round exists was not in
  the build that playtester ran; a fix claimed
  against a DIFFERENT build was not in it either. Either way the board leaves
  it amber and says why, and the filing warns you the moment it spots the
  mismatch.
- **`game` on every playtest filing (MUST).** The board's live issues ride the
  round as the playtester's checklist after free play. It costs no step budget,
  adds ~30 seconds per issue inside est_minutes, and is the ONLY path to
  `verified`. Omit it and the round has no memory.
- **Never leave a playtester-filed issue untriaged (MUST).** A bug reported
  from inside a round lands `open` with origin `reviewer`, and answering it
  is part of reporting that round — accept it, or close it duplicate /
  invalid / cannot_reproduce. The board keeps that queue and prints it as
  "Needs triage". Both the results and your own `create` name any live issue
  that looks like the same bug ("possible duplicate of #4"): read the pair
  before accepting, and if it is one, close the newer with `reason:'duplicate'`
  and `duplicate_of_seq`.
- **Where the checklist is answered today, honestly.** The Windows browser
  runner renders it; so do the current Windows recorder app and the reviewer
  app on macOS/iOS native rounds — but a playtester on an older build of
  either sends no checklist at all, and WEB rounds render none by design.
  Never infer this from the platform: the results say it per session. Four
  kinds of silence, none of them interchangeable — "Didn't reach" (never got
  there), "Couldn't test" (got there, still could not tell), a blank row (shown
  the checklist, said nothing about this one), and `not shown to N players`
  (that session's client never rendered a checklist, so its silence is evidence
  of nothing whatsoever). An issue nobody answered never moves, and you
  never report an unanswered checklist as "no longer reproducing".
- **A `self_run: true` result is YOU, not a playtester (MUST).** A developer can
  run their own round from the round's page — free, and marked by the service.
  Report it as the developer's own session in the same breath as its answers:
  it is never independent evidence, it never counts toward the round's
  playtester count, and a "Gone" it gives a claimed fix verifies nothing (the
  board records it and moves on). What it CAN do is fail: a "Still here" from a
  self-run regresses a fix you claimed, and a bug filed from one lands on the
  board like any other. A round whose only results are self-runs has not been
  playtested yet — say so in the headline instead of reporting it as a pass,
  and file a real round before you tell the dev the fix holds.
- Nothing on the board costs credits — only rounds do. `qaping issues <game>`
  reads the same board from the shell.

## The review interface (know your tester)

\<!-- Distilled from QAPING_REVIEWER_INTERFACE.md (monorepo root, INTERNAL,
     code-cited). Re-derive there when a reviewer surface changes. -->

Binding, derived from the review interfaces' code. The person who claims a
web round is on their phone, scrolling a feed. They read `instructions`
BEFORE claiming — front-load hardware and requirements there so the wrong
tester never claims. On claim the game auto-loads into an embedded browser
view with your steps beside it on the same small screen, with zero context;
attention is highest in the first minutes; setup friction is unpaid time.

The tester CAN: play the already-loaded game (touch, scroll, type); go
Back; Reload — which KEEPS storage, so a reload is never a fresh state; see
all steps at once and answer in any order; tap ONE option per option step;
type a note on any question step; pin a comment to a page element and draw
on it; pick one verdict; bail out with a reason.

The tester CANNOT:
- open tabs or windows — window.open and target=_blank links are dead
  INSIDE the game too, so a game whose Play button opens a new window is
  broken-for-review: flag it to the dev instead of filing;
- type or edit a URL: the round's `url` is the only page-load there is, and
  links in step text are inert on the phone — never put links in steps;
- clear storage or go incognito: fresh state comes ONLY from a setup URL
  param the round's `url` already carries;
- use devtools, attach files, or record — web rounds return answers only;
- use a second device;
- see `instructions` or `expected` once inside the review — EVERYTHING the
  tester needs at answer time lives in the step text (≤300 chars each).

**Steps speak player language (MUST).** Things to tap and see in the game —
never flags, URL parameters, storage, or code concepts. A test hook is
exercised by the ROUND's `url` carrying it; the step describes only the
player-visible expectation ("the How to play option should be offered
first"), never the mechanism. Never ask to close/reopen anything or "start
fresh" — that state is a separate round whose `url` forces it. And as
always: one action per step, exact UI labels (the button says "Continue",
not "the resume option"), the most important check first, and never a step
that assumes they read your repo.

## SETUP — author QA-PLAN.md (first run in a repo)

1. Read the game repo: engine, how a shippable build is produced, save system,
   settings, input devices the game supports.
2. Ask the dev ONCE for their build command (the one command that produces a
   shippable build) and which platforms they ship; record both in the plan's
   frontmatter so every future run can build without asking again.
3. Author `QA-PLAN.md` at the repo root in EXACTLY this format (self-contained
   here — do not go looking for other docs). Plan frontmatter (YAML at the
   very top): `game`, `game_slug`, `build_command` (the ONE shippable-build
   command), `platforms: [windows|macos|ios|web]` (`web` = a browser-playable
   game — its "build" is a static directory, not a zip), optional `input`
   (hardware; default keyboard+mouse, or touch for a mobile-web game).
   **Mint `game_slug` ONCE**, from the game name: lowercase, every run of
   non-alphanumerics collapsed to a single `-`, no leading or trailing `-`,
   ≤64 chars ("Solar Drift" → `solar-drift`). It is the issue board's id and
   is NEVER renamed — the same rule check ids live under, for the same reason:
   a renamed slug orphans every issue filed under the old one.
   Then one `##` section per check — the heading is the check's short name —
   opening with a fenced yaml block of `id` (stable slug, never renamed),
   `rung: human | code`, `origin` ("authored" or the round id that
   last changed the check definition), and optionally
   `setup` (the link or flag that forces this check's precondition — see
   "Make the build testable"), followed by the steps as numbered prose a
   playtester who has never seen the game can follow. Author each check to
   end in an observation ask, with its precondition stated as a verifiable
   step-zero fact (forced by `setup`, else verified by an opening question).
   A `rung: code` check keeps its prose and adds one `test:` line naming the
   repo test that asserts it. Order checks critical-path first, then
   game-specific ones:
   1. the game boots to the main menu
   2. a previous-version save loads
   3. the first 15 minutes play clean on the declared input hardware
   4. the core loop works (name it concretely — the thing this game is)
   5. settings persist across a restart
4. **Enter each check at the right rung.** A check that is mechanically
   assertable — a save file loads, a config parses, an asset path resolves —
   enters at `rung: code` from day one: write the repo test then and there,
   never "start it human and promote later". Human rounds are reserved for
   what only a human can judge. Where a save must still be human-tested, the
   dev provides the fixture: the previous release's save ships inside the
   build (or seeds via URL param on web), named in the check's steps — a
   stranger in a fresh browser cannot possess your old save.
5. **Gyms**: for a mechanic worth isolating, you may build a tiny
   deterministic test scene or page in the dev's repo — one mechanic,
   machine-readable pass/fail. Ordinary dev work; offer it, never force it.
6. Tell the dev how runs get triggered, honestly: for now the loop runs from
   their own machine or agent — after a patch lands, they say "run QA on this
   patch". Do NOT offer to wire a CI workflow file: a plain CI runner has no
   qaping MCP connection and no login, so a committed workflow could not run
   this loop today; a CI-triggered recipe is a documented follow-up. Until it
   ships, per-patch QA is an ask-your-agent step.
7. Show the dev the plan and commit only on their approval.

## Make the build testable

Before publishing a test build, you SHOULD add test affordances to the dev's
own code — ordinary dev work that turns self-reported state into forced,
verifiable state:

- URL params or flags that force states: `?fresh=1` (a true first visit),
  `?difficulty=medium`, `?state=<checkpoint>` (start at a checkpoint).
- Bundled save fixtures plus a load control (the previous release's save,
  shipped in the build).
- Seeded randomness, so a reported oddity reproduces.
- A corner build stamp (build hash + first-run/save-state flag; a `?qa=1`
  overlay on web) with a step asking the tester to read it back — a read-back
  fact is verified; self-report is not.

Record each check's hook in its `setup` field; at filing time the hook
rides the ROUND's `url` — the game loads it itself, so the tester never
sees or types it — and the filed step states only the player-visible
expectation. The unreviewed-developer-build disclosure
already covers shipping these; the no-steering rule forbids steering SAFETY
decisions only. A store-delivered build that cannot surface state keeps its
checks testimony-only — mark that in the plan and report at that grade.

## RUN — per patch

0. **Read the board.** `qaping_issues` with the plan's `game_slug` (action
   `list`): what is open, what you claimed fixed and is still waiting on a
   playtester, what came back REGRESSED, and the two queues the board keeps
   for you — "Needs triage" (playtester-filed bugs you never answered) and
   "Never answered" (issues that have ridden three or more checklists with no
   answer either way). Both are worked in this run, not noted for later. This
   is the bug half of "what happened since last time"; server reports are the check half: read `qaping rounds --processed --game
   <game_slug> --json`, including imported `workflow.legacy.history`. Carry
   unresolved non-bug follow_ups forward in the next report; omit one only
   after it is done or explicitly deferred with a reason.
1. **Select.** Read the diff (or PR). Pick the checks it can plausibly affect,
   plus the always-run criticals (the critical-path block above) and every
   check the latest server reports left NOT-ASKED or Blocked. Tell the user which
   checks run and why.
2. **Compose sessions.** Partition the selected checks by required state —
   fresh-install / progression / settings-mutating — and put state-mutating
   checks LAST within their session. A session has ONE state: its round
   `url` (carrying the forcing setup param) is the only state control that
   exists — testers cannot clear storage or start fresh themselves — so
   checks needing different forced states never share a session. Budget play content: sum the checks'
   directed play time; if it exceeds est_minutes, split into parallel
   5-minute rounds (credit-neutral: two focused 5-minute rounds cost one
   diluted 10-minute round) or raise est_minutes within the cap, and state
   the trade beside the cost estimate. Depth beyond the budget rotates across
   patches; note in the plan which slice ran last.
3. **Build** via the recorded build command, with each selected check's
   `setup` affordance in place; zip the result (native) or keep the built
   static directory (web).
4. **Ship**, by delivery: NATIVE uploads — `qaping publish-build <game.zip>
   --platform windows|macos` → prints a `/b/<slug>` URL (temporary hosting;
   filing a playtest extends the build through the round; a CHANGED build gets
   a new URL, while re-publishing an unchanged zip returns the same build).
   You hold only a handful of hosted builds at once: if a publish is refused
   for that cap, `qaping builds` lists what you are holding and
   `qaping builds rm <slug>` frees a slot — do that and carry on rather than
   stopping to ask. The listing marks each build: never-finished uploads are
   safe to delete first, and any build an open round is still using is marked
   `IN USE` — never delete one of those, whichever session filed it. If every
   build is in use, say so and wait for a round to finish rather than guessing. Store-delivered games file with their Steam store
   page, TestFlight public link, or App Store page as `url`. WEB games — host the built output
   at a public URL: the dev's own hosting if they have it, else
   `qaping publish <built-dir>` prints a hosted URL. Localhost never works —
   players open the link on their own devices. When filing a WEB game: send
   `url` + `est_minutes` and OMIT `platform` entirely — a web round is claimed
   by players in their own browser, phones included.
5. **Claim fixes (MUST, before filing).** For every board issue this patch
   fixes: `qaping_issues` `action:'fixed'` with its `seq`, `build` set to the
   exact URL this round will play — the `/b/<slug>` or store URL you just
   published, character for character — and a `note` written for the
   playtester ("the shop stays open now"). Claim first, file second, and claim
   against THE BUILD: a claim recorded after the round exists was not in what
   that playtester ran, and a claim naming a DIFFERENT build was not in it
   either. Both leave the issue amber; the filing prints the mismatch when it
   sees one, and a "Gone" against another build verifies nothing. Re-claim
   against the URL this round actually plays rather than spending the round on
   an answer that cannot count. No build URL, no claim. Then pin what you
   claimed (step 6).
6. **File** ONE `qaping_playtest` per composed session. The standard 11-item
   player-experience questionnaire is required on every playtest, including
   QA-PLAN rounds; it cannot be disabled. Omit `questionnaire` or send
   `questionnaire:'standard'`. Your checks are appended after it. Always
   set `game` to the plan's `game_slug` (MUST), so
   the board's live issues ride the round as the playtester's checklist.
   Pin with `issues` (MUST when the round exists to settle something specific):
   the seqs you claimed fixed in step 5, plus any the board lists as never
   answered, ride ahead of even a blocker. Never pin more than the round
   carries — 8 issues at 5 minutes, 18 at 30, 20 at the ceiling — because an
   over-long pin list is REFUSED, not trimmed, and a seq that is closed or not
   on this board refuses the filing too.
   A WEB session additionally files `require_evidence:'none'` (MUST) — left
   at its default, the finish silently demands a pinned
   screenshot-comment no step asked for. est_minutes is an
   honest sum of the steps' directed play — the service
   accepts 5–120 minutes (10 is the standard session, and a QA-plan round
   rarely earns more than 30; outside 5–120 the filing is refused, not
   clamped), and the clock is play time:
   download/install happens before it starts. The authored steps MUST be:
   - **one step per selected check**, its text opening with the id token —
     `[spin-readable] …` — the plan prose rewritten as an observation
     question ("describe what the start menu showed and what you tapped
     first", never "confirm the menu appears"), with options exactly
     ["Pass — as described", "Fail — describe exactly what you saw",
     "Couldn't test — say why", "Didn't reach this part"] — the pick comes
     back verified in steps_result. EXCEPTION: when the check asks the
     tester to DISCRIMINATE between named states ("which difficulty did the
     bot play like?", "which screen did you land on?"), the options are the
     NAMED candidates themselves ("rookie-level" / "harder than that") plus
     "Couldn't tell — say why" — generic Pass/Fail on a discrimination
     yields contradictions instead of a signal (measured live);
   - option labels ≤40 chars, 2–4 options per step; never author a final
     step whose options duplicate the verdict options — the phone hides it
     as a duplicate of the verdict control;
   - a check with a `setup` hook is forced by filing the session's `url`
     WITH the hook — the game loads it itself; the step states only the
     player-visible expectation. One whose precondition cannot be forced
     opens with a verifying option step ("Before this session: had you ever
     played this game before?" — yes / no / not sure);
   - **a recheck of a known bug is NEVER a step.** The board rides the
     checklist: `game` on the filing attaches the board's live issues, the
     playtester answers each one (Still here / Gone / Couldn't test / Didn't
     reach) after free play, and that costs none of the step budget. Never
     author a step that re-asks an issue already on the board — a step and a
     checklist row about the same bug buy one answer twice — and prior
     findings stay OUT of `instructions` entirely, so the rest of the pass is
     an independent look;
   - a closing **break-it slice** (~2–3 minutes) authored from the diff:
     "this patch changed X — try to break it: \<concrete abuse ideas from the
     diff>. Report the weirdest thing you saw AND list what you tried."
     Abuse ideas target PLAYER-VISIBLE behaviors the diff changed — things a
     player can tap, see, or provoke — never internal mechanisms (a flag, a
     cache, a storage key means nothing to a player).
     Finding nothing is a fine answer when we know what was attempted; frame
     it in `instructions` as "these checks are the territory — break anything
     near them";
   - hardware verification where it matters: needs beyond keyboard+mouse go
     up front in `instructions` AND an explicit step asks which input device
     was actually used, with options.
   Send `qa_context` with this session's selected check ids and known patch,
   commit and PR context in the SAME playtest call.
   **Filing gate (MUST):** print `this round covers: <ids>` per session and
   assert the ids — unioned across every session this run files — equal the
   Select step's list BEFORE calling qaping_playtest. The wire keeps only
   the FIRST 20 steps_result rows. The play directive and required 11-item
   questionnaire occupy 12, so budget at most 8 authored steps per session,
   including hardware, precondition and break-it questions. Larger lists are
   rejected before filing to keep answers from being silently dropped at finish. A
   mismatch (the budget forcing cuts) fails loudly PRE-SPEND: batch another
   session or state the deferral out loud — never silently truncate. Then
   print `issues: <seqs attached>` from the filing's own result (it names the
   checklist it built, which of them you pinned, and anything the round's own
   cap left off), or `issues: none` on an empty board — so what this round
   RE-CHECKS is on the record beside what it covers.
7. **Wait or park — decide now** (ground rule 1). Every filing carries
   `qa_context` with the selected check ids and known patch/commit/PR context.
   WAIT: spawn a background task looping `qaping_wait` and keep working —
   foreground polling is the fallback. PARK: the filing already carried an
   explicit `deadline_seconds` sized to the span and is saved on the server.
   Tell the user what is pending and end the turn; a later session collects it.
   A promise to check later is never a wait. No local round record is needed.
8. **Report** from `qaping_results`, after claiming the round as above:
   - **Evidence line first (MUST).** Every report opens with its grade:
     `Evidence: recording + transcript` (macOS/iOS, or a Windows result with
     `transcript_status:'ok'`) / `Evidence: recording only` (a Windows result
     with `transcript_status:'unavailable'` — a Game Bar session) /
     `Evidence: testimony only (web round)`.
   - **Computed headline (MUST).** Derive the one verdict sentence from the
     per-check outcomes, never from the tester's own verdict: `PASS` only
     when every selected check returned Pass; `PASS — N unverified (<ids>)`
     when nothing failed but any check is Blocked or NOT-ASKED; `FAIL: <id>`
     on any Fail. Quote the tester's global verdict beneath it as one input —
     it is never the headline. (The iterate rule already says unresolved
     findings mean fix and refile — unresolved never headlines as PASS.)
   - **Issues line (MUST), under the headline.** One line read off the
     results' issue block: `issues: #3 verified, #5 REGRESSED, #7 unreached,
     2 new` — verified first, regressions next, then `unreached` for the
     issues whose only answer was "Didn't reach" (nobody got to them: they
     were not tested and the board did not move), then how many bugs
     playtesters filed from inside the session. `issues: none moved` when the
     board rode along and nothing changed; nothing at all when the round
     carried no `game`. Two qualifiers from that block never get dropped on
     the way into the line: `1 of 2 confirmations` means the fix HELD for that
     player and needs one more — report it as holding, never as verified, and
     buy the second with the next round; `not shown to N players` means those
     sessions never rendered a checklist at all, so name that instead of
     counting them as silence. A REGRESSED issue is a failure of a fix you
     claimed: say so in words, in the same breath as the headline.
   - **Mine the transcript for what nobody typed (MUST, wherever a transcript
     exists).** Read every session's think-aloud transcript for bug-shaped
     moments the typed answers never covered — "it didn't", "nothing
     happened", "crashed", "stuck", "I can't", "again" — and file each as a
     board issue (`action:'create'`) whose body QUOTES the player, in their
     language, with an `area`, the round's `ping_id`, and the stamp the
     transcript gave it sent as `time_ms` ([12:34] → 754000) so the report links
     straight to that moment. The board IS the draft: never open a GitHub issue for a
     transcript moment before it has been triaged on the board. Two limits,
     both MUST: never file a moment the same session already reported in an
     answer or a new bug — that is a duplicate of a row you already have — and
     never file more than FIVE per session without asking the user first,
     because a transcript is full of grumbling and a board nobody can read is
     a board nobody re-checks. A round with no transcript (a Game Bar Windows
     session, a web round) skips this step, and the report says the mining did
     not happen rather than implying a clean transcript.
   - **Work the board's two queues (MUST).** The results block ends with them.
     `Needs triage: N` is playtester-filed bugs with no `external_ref` yet —
     clear it by triaging (below). `Never answered` lists issues attached three
     or more rounds that nobody has answered either way — for each one, pin it
     on the next filing, give that round a `setup` link and a step that walks a
     player to it, or close it, and name the choice in the report. Neither
     queue survives a run untouched.
   - **One row per SELECTED check (MUST)**, keyed by id, outcome from
     \{Pass, Fail, Blocked, NOT-ASKED\}. "Couldn't test" and "Didn't reach this
     part" are Blocked, with the why. A check that reached the wire as more
     than one row (a precondition step plus its observation step) takes its
     outcome from the WORST row: any Fail → Fail; else any Blocked or
     unanswered row leaves the check unverified and the headline counts it
     ("PASS — N unverified") — never plain Pass over a Blocked sub-step. A
     check whose precondition came back unverified or disproven is VOID —
     report it as Blocked ("VOID: precondition unverified"),
     never as a pass or fail, and do not treat it as a verification. A selected check that never made the wire or
     never came back is NOT-ASKED and carries forward into the next filing
     automatically. Cite [mm:ss] where a transcript or recording exists; on a
     web round cite the step answers — there are no timestamps to cite.
   - PR comment via `gh pr comment`: evidence line, the computed verdict
     sentence first, then the per-check rows, then credits spent.
   - **Save the report on the server (MUST).** Send JSON with
     `qaping rounds complete <ping_id> --token <token> --revision <revision>
     --responses <comma-separated response_ids, or none> --report -`
     (JSON on stdin; a temporary JSON file also works). Use the token, revision
     and response ids captured BEFORE reading the results. The report is:
     `{"evidence_grade":"testimony only (web round)","verdict":"PASS",
     "checks":[{"id":"boot-to-menu","outcome":"Pass"}],
     "follow_ups":[],"external_refs":["<PR comment URL>"],"summary":"<report text>"}`.
     `checks` includes every selected id exactly once. `follow_ups` holds
     unresolved NON-BUG follow-ups — bugs stay on the issue board. Optional
     per-check `note` explains Blocked/VOID or a failure. Optional `summary`
     preserves the rendered report, including the issues line. Build, credits,
     player answers and issue transitions remain service facts; do not submit
     copies as top-level report fields. This report is the AGENT'S interpretation,
     never player evidence, and cannot verify a board issue.
     Completion atomically saves the report and marks it processed. Retry the
     EXACT same payload/token on an uncertain reply; it cannot create a second
     report. On 409, read and claim again: a response or transcript may have
     arrived. Never reuse an old report over new evidence without reviewing it.
     Previous reports remain in `workflow.report_history`; late evidence
     reopens work instead of silently disappearing. Do not write a local ledger.
   - Update `QA-PLAN.md` only when check definitions change; record the source
     round as `origin` for such an edit. Read execution outcomes and verification
     history from server reports, not local `state` or `last_verified` fields.
   - **QA memory (standing rule, not just here)**: whenever the developer
     mentions — in any conversation — something that should always be tested,
     a fragile area, or a QA lesson learned, offer to record it as a check
     (or a note on an existing check) in `QA-PLAN.md` right then, so the plan
     accretes knowledge instead of losing it to chat scrollback.
   - **Triage every new issue in THIS turn (MUST).** Each `NEW #n` in the
     results is a bug a playtester filed from inside the session, and it is
     answered before the report is finished: accept it (`gh issue create` for
     the dev's triage, then `qaping_issues` `action:'edit'` with
     `external_ref` set to that URL, and an `area` if it arrived without one),
     or close it — `duplicate` with `duplicate_of_seq`, `invalid`, or
     `cannot_reproduce`. When the results flag one as a `possible duplicate of
     #N`, read both rows before accepting: usually it is one, and closing the
     newer with `reason:'duplicate'` keeps the checklist honest instead of
     spending two rows of it on one bug. Never leave one sitting; an
     untriaged board stops being worth reading, and the next round re-asks a
     bug nobody decided about.
   - **A REGRESSED issue reopens its mirror (MUST).** The fix did not hold:
     `gh issue reopen <n>` on the GitHub issue, name it in the PR comment,
     and never claim `fixed` on it again without a new build to claim
     against.
   - **A verified issue closes its mirror.** An issue a playtester turned
     `verified` is settled: close the GitHub issue citing the round. Leave
     the board row green — never `action:'close'` a verified issue to tidy
     up; closed is for what you decided about, not for what was confirmed.
   - Findings YOU file: one board issue per finding (`action:'create'`, in
     player language, with an `area`, severity from consequence — `blocker`
     cannot play past it / `major` / `minor` / `cosmetic`, and remember a
     blocker or major needs two playtesters to say Gone before its fix turns
     verified), then one `gh issue create` per finding as the dev's own draft
     — never near-duplicates, never one issue per symptom of the same bug —
     and `action:'edit'` the board row with the `external_ref` you just
     created. Before reproduction the body carries
     "observed once, unreproduced" plus that proposed severity. The label
     CONFIRMED is reserved for a targeted round or unambiguous in-round
     evidence; a CONFIRMED issue carries repro steps rebuilt from the
     tester's answers and a timestamp link into the recording where one
     exists (web rounds have none — cite answers).

## The ambiguity ladder

An `ambiguous` or first-time-failing check never re-runs inside the next
batch — it refiles ALONE as a targeted ~5-minute round: one check, its
precondition forced via `setup` (or verified by the opening option step),
plus the disambiguation steps. That round settles it: Pass → `passed` (note
the fluke); Fail → `failing`, and the issue upgrades to CONFIRMED. Never
resolve an ambiguity by re-buying the whole batch, and never label a
once-seen fail CONFIRMED without that round or hard evidence. When the
targeted round settles it as a real bug, the board issue for it carries
`check_id: <the check's id>` — set at `create`, or with `action:'edit'` on a
playtester-filed issue — so the check and the bug that made it ambiguous stay
findable from each other.

## Paired rounds (two-state comparisons)

A feel/physics/balance regression judged absolute buys little — a stranger
answers "did spin feel right" in a vacuum. But a comparison never rides one
round: never two links in one round — links in step text are inert on the
phone and `instructions` go unread in-review, so a second URL simply never
gets opened. When a check needs TWO states compared (with/without a hook,
old build vs new), file TWO paired rounds with the SAME steps, one per
state, each state forced by its own round `url` (the server round's `build` field
keeps the old build recoverable), and compare the answers yourself in the
report. Caveat it: different testers played each side, and a tester told to
hunt changes reports noise as change. Native builds pair the same way, one
build per round — re-publish the previous zip if its /b/\<slug> expired.

## Player-experience scores (every round)

The standard 11-item player-experience questionnaire is required on every
round, alongside any QA-PLAN checks. Report its scores separately from the
per-check outcomes: a rating never proves that a check passed. At milestones,
additional coverage can be an experience round with no custom checks and
n_target up to 3 players, priced
transparently (est_minutes × 2 × players — state it first). Single-tester
scores are trend data — meaningful only after 3+ rounds on the same game,
never compared across testers or builds at n=1. If 8 or more of the 11 scale
answers are identical, report "low-differentiation response — treat scores as
unreliable" and never average them into a comparison.

## PROMOTE — make the suite cheaper

When a check has passed and is mechanically assertable — a save file loads, a
config parses, an asset path resolves — offer to write a normal test in the
repo's own test suite; the server's per-check report history is the evidence
that justifies the offer. On the dev's yes: write the test, flip the check's
`rung` to `code`, keep the prose (it documents intent) and add a `test:` line
naming the test file. `rung: code` checks then run in the dev's own CI for
free — that is the point: every check starts as human as it must and gets
cheaper over time. Checks about feel, difficulty, or ambiguous visuals stay
`rung: human` permanently. Never delete or demote a human check without the
dev agreeing.
