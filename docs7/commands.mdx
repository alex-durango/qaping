Everything the `qaping` binary does. Your agent runs most of these for you;
`setup`, `builds` and `rounds` are the ones you will type yourself.

On Windows PowerShell, use `qaping.cmd` wherever this reference says `qaping`.
For first-time setup, follow [Install on Windows](/windows).

```
qaping setup [claude-code|cursor|codex] [--force]
qaping remove [--client <c>]
qaping publish-build <game.zip> --platform windows|macos
qaping builds
qaping builds rm <slug>
qaping publish <built-dir>
qaping wait <ping_id> [--timeout <seconds>]
qaping results <ping_id> [--json]
qaping rounds [--game <slug>] [--all|--processed] [--limit 1-100] [--cursor <cursor>] [--json]
qaping rounds show <id>
qaping rounds claim <id> [--token <uuid>]
qaping rounds release <id> --token <uuid>
qaping rounds context <id> --revision N --data <json-file|->
qaping rounds complete <id> --token <uuid> --revision N --responses <id,id|none> --report <json-file|->
qaping rounds import [--directory <path>] [--dry-run] [--json]
qaping issues <game> [--json] [--status open|fixed|verified|closed]
qaping whoami
qaping version
```

## Getting in and out

### `qaping setup [claude-code|cursor|codex] [--force]`

Registers the qaping MCP server with your coding agent, installs the `qaping`
skill and its rule, and signs you in (a browser window opens once). With no
client name it detects what is installed. `--force` rewrites an existing
entry.

### `qaping remove [--client <c>]`

Removes qaping's MCP entry, skill and rule from the client. It touches only
qaping's own state — nothing else you have installed, and not your login.

### `qaping whoami`

Which account this machine is signed in as. Results are scoped to the account
that filed the round, so check this before deciding a round is gone.

### `qaping version`

Prints the installed version.

## Hosting a build

### `qaping publish-build <game.zip> --platform windows|macos`

Uploads a zipped native build and prints the `/b/<slug>` URL a round is filed
against. You hold a small number of hosted builds at a time; the oldest is
listed first by `qaping builds`.

### `qaping builds` / `qaping builds rm <slug>`

Lists the hosted builds you hold, or deletes one now to free its slot.

### `qaping publish <built-dir>`

Hosts a browser-playable game's built output and prints the public URL. Web
rounds are filed with that URL and no platform.

## Rounds

### `qaping wait <ping_id> [--timeout <seconds>]`

Waits on a filed round, renewing the lease that keeps it visible to new
playtesters, and prints the results when they land. The agent normally runs
this in a background task.

### `qaping results <ping_id> [--json]`

One passive fetch, no waiting. Exit code `0` means results are in, `2` means
still pending, `1` anything else (expired, not yours, unreachable).

### `qaping rounds`

Lists unprocessed playtest work from the server, from any directory. Optional
`--game <slug>` scopes it to the game in QA-PLAN.md. No local ledger is read.
A server error fails loudly; it never falls back to stale local records.

### `qaping rounds --all`

Includes processed history; `--remote` is an alias. `--processed` lists only
processed reports. `--json` returns round facts plus private workflow context,
report, legacy history and processing state. Pages hold up to 50 rounds by default (report-heavy pages can be smaller);
`--limit 1-100` changes the size and `--cursor <next_cursor>` follows older pages.

### `qaping rounds show <id>`

Reads a round's full private workflow, previous reports and current response ids.
The original build and game come from the round itself. Reading never marks it
processed. All individual workflow commands return JSON.

### `qaping rounds claim <id> [--token <uuid>]`

Claims a ready/expired report for collection. Returns a collector token, revision
and response ids to retain BEFORE fetching results. Claims last 30 minutes;
repeat with the same token at least every 20 minutes to renew. Another collector
cannot take a live claim. Reuse the same token if a reply is lost (the CLI prints
it with the error). A crashed session's claim expires automatically.

### `qaping rounds release <id> --token <uuid>`

Releases a claim without marking work processed or removing the round.

### `qaping rounds context <id> --revision N --data <json-file|->`

Replaces an unprocessed round's private context: optional `checks`, `note`,
`commit` and `pr_url`. Read `show` first and preserve fields you want to keep.
A stale revision or active collector is a conflict. For new rounds, send this
as `qa_context` on the playtest filing so it is saved atomically from the start.

### `qaping rounds complete <id> --token <uuid> --revision N --responses <id,id|none> --report <json-file|->`

Saves the agent's report and marks it processed atomically. Pass the token,
revision and response ids captured before reviewing results; `none` represents
an empty array. The report requires `evidence_grade`, `verdict`, typed `checks`
and unresolved non-bug `follow_ups`; `external_refs` and `summary` are optional.
See [the report format](/qa-plan#round-state-and-history-live-on-the-server).
The report is an agent interpretation, never a replacement for player evidence.

An identical retry is safe. A conflict means the claim expired or results changed;
read and claim again. Late evidence reopens work while preserving the old report.
External PR comments should use a stable round-id marker so retries update them.

### `qaping rounds import [--directory <path>] [--dry-run]`

Imports legacy `qa-open-rounds.json` and `qa-rounds.jsonl` from the current or
specified directory once. It validates both before writes, preserves original
records on the server, and never rewrites the files. Retry after an interruption;
already-imported rounds are skipped. Unknown or wrong-account ids fail loudly.
After import the originals are backups, not live inputs. `rounds add` and `rounds rm`
are retired and fail with migration instructions instead of changing local state.

## The issue board

### `qaping issues <game> [--json]`

Prints the game's issue board: every bug that outlived a round, with its
status — open, fixed (you claim it is fixed), verified (a playtester
confirmed it is gone), closed. Each bug prints as one compact line — number,
status, severity, the part of the game it lives in, the title — over a second
line of counters: how close a claimed fix is to being confirmed ("1 of 2
confirmations"), how often the bug has been seen, how often players never
reached it, and the build a fix was claimed against.

Two queues bracket the list whenever they have anything in them.
**Needs triage** prints first: bugs a playtester filed that your agent has not
linked to your own tracker yet. **Never answered** prints last: bugs that have
ridden three or more rounds with nobody answering either way — the agent is
supposed to pin them, reach them with a setup step, or close them. Both are
the agent's work, and both are visible here so you can see whether it is doing
it.

`--status open|fixed|verified|closed` prints one status only; without it you
get open, fixed and verified, because closed issues are history. `--json`
prints the machine-readable rows.

Read-only, on purpose. Your agent files, claims, closes and reopens issues
through the `qaping_issues` MCP tool while it runs the loop; this is the
window you read it through. Nothing on the board costs credits — only rounds
do — and nothing turns *verified* except playtesters answering "Gone" on a
round filed after the fix was claimed, against the build that round played:
two of them for a blocker or a major, one for a minor or cosmetic.

## Files qaping leaves in your repo

| file | what it is | commit it? |
|---|---|---|
| `QA-PLAN.md` | the checks this game must pass; the agent authors, you own | yes — see [the format](/qa-plan) |
| `qa-rounds.jsonl`, `qa-open-rounds.json` | legacy backups only; import once | existing files are preserved |

The issue board is not a file: it lives on the service, one board per game,
and `qaping issues <game>` reads it. The plan's `game_slug` is what names it.
